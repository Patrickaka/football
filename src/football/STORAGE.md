# 足球存储保留与无损归档

本次只改变存储方式，主页面、模型概率及首份赛前评估口径不变。

| 对象 | 默认规则 | 完整性 |
| --- | --- | --- |
| 临时情报缓存 | 保留 7 天、每场最多 8 份；全局维护后受管理 JSON 总量目标不超过 256 MiB | 冻结预测自带证据副本，不依赖缓存继续存在 |
| 同场重复重算 | 模型、概率、盘口、证据等一致，仅外层运行时间变化则复用原事件 | 不修改原事件的时间、hash 或 ID；证据发布时间/采集时间变化仍视为真实变化 |
| 同场不同预测 | 常用列表保留首份和最近 7 份，较早的独特事件压缩保存在同一记录内 | 所有事件仍可恢复，首份永远不替换；完整导出按原顺序还原 |
| 已结算历史 | 结算满 30 天后，压缩比分事件、盘口时间线、情报快照等大字段 | gzip + base64，无外部归档文件；解压长度、SHA-256、字段清单均校验；读取自动恢复 |

历史压缩只有节省至少 1 KiB 且至少 10% 才生效。无时区、未知或未来的结算时间不猜测、不归档。数据库索引列、比赛信息、赛果、主要统计字段继续直接可读。新格式由足球主表的仓储接口处理，其他业务表不变。

## 自动运行

已接入现有启动维护和定时维护线程，默认每 6 小时运行。情报写入后立即执行该场的年龄/数量限制，全局容量在完整维护时整理。历史归档每轮检查最多 200 条符合年龄条件的记录，后续轮次继续，避免启动时扫描并重写整库。

已压缩记录不重复写库。MySQL 仅按主键更新单条文档，并比较更新前原文；发生并发赛果订正则跳过，不覆盖新赛果。当前单 worker 下，JSON 回退写入与预测写入共用记录锁，临时文件写完并同步后原子替换；发现文件已变化则跳过。独立多进程写同一回退文件仍需沿用项目的单 writer 部署约束。

缓存清理只操作模块自有目录/文件格式，拒绝 symlink、junction 和越界路径，使用线程及跨进程文件锁。未知文件、损坏或无法验证归属的超大文件会保留并报错，因此 256 MiB 是受管理快照的目标，不是整个目录无条件硬删至该大小。孤立临时文件至少等待 1 小时；30 分钟读取 TTL 与删除规则分别生效。

## 查看或立即执行

在项目根目录执行：

```powershell
# 默认只预览，不清理或写库
.venv/Scripts/python.exe scripts/tools/football_storage.py --dry-run

# 执行，并保留本次报告
.venv/Scripts/python.exe scripts/tools/football_storage.py --apply --output reports/football-storage-maintenance.json
```

报告中缓存 `planned_*` 为预计清理量，`removed_*` 才是实际删除量。历史归档 `bytes_saved_estimate` 表示紧凑 JSON 文档体积的减少，不能直接当作 MySQL 磁盘文件已释放的字节。不会执行 `OPTIMIZE TABLE`、清空表或删除预测记录。全量 JSON 导出会还原证据，因此导出文件仍可能较大。

可选配置：

| 环境变量 | 默认值 |
| --- | --- |
| `FOOTBALL_INTELLIGENCE_RETENTION_DAYS` | `7` |
| `FOOTBALL_INTELLIGENCE_MAX_SNAPSHOTS` | `8` |
| `FOOTBALL_INTELLIGENCE_MAX_BYTES` | `268435456`；`0` 关闭容量限制 |
| `FOOTBALL_PREDICTION_EVENT_ACTIVE_LIMIT` | `8`，最小 2 |
| `FOOTBALL_ARCHIVE_AFTER_DAYS` | `30`；`0` 允许结算后立即压缩 |
| `FOOTBALL_ARCHIVE_BATCH_SIZE` | `200` |

无需下载模型、新建数据库表或新增数据库服务。更新服务代码后启动/定时维护自动生效。部署回退到不支持该格式的旧代码前，应先用当前版本完整导出备份并恢复兼容文档；不要直接让旧读取器读取压缩字段。
